# 过号重叫位次架构决策（ADR）

## 决策（全局唯一，禁止混用另一臂）

采用 **「插回原位次」** 臂：号牌的 `queue_pos` 在取号时一次性分配，
在当日同业务种类的**活动号牌**（`等候/叫号中/办理中/过号`）内唯一且单调，
**终身不重排**。过号保留原位次；重叫带着过号前位次直接占窗，不写 `queue_pos`。

明确不采用 **「重叫排到队尾」** 臂：任何读路径不得把重叫号按新位次沉底展示，
代码中也不存在「重叫重算位次」的分配逻辑。两套口径不得在同一系统混用。

## 位次编码

- 取号：`pos = MAX(queue_pos) + 1`，统计范围为当日同种类**活动**号牌；
  已办结/已作废释放槽位，其位次号可被后续取号复用，但号牌本身（`slip_no`）不复用。
- 过号：仅改 `status='过号'`，`queue_pos` 原样保留。
- 重叫：仅改 `status='办理中'`、`window_id`、`called_at`，**不触碰** `queue_pos`。

## 读路径重放规则（单一事实来源）

所有读路径——过号回收列表、等候队列投影、等候墙分栏、在办栏——
位次一律由同一条规则重放：

```sql
ORDER BY queue_pos, id
```

- 等候墙种类分栏只投影 `等候/过号`（`WALL_COLUMN`），栏内按 `queue_pos` 升序，
  过号**不沉底**；
- `叫号中/办理中` 由窗口当前号指针反查的「在办」栏承接，与种类栏互斥、不重复；
- 叫号选号同为该规则的直接重放：`status='等候' ... ORDER BY queue_pos, taken_at, id`；
- 事件流（`call_events`）完整记录 `叫号→过号→重叫` 轨迹，可核对位次从未改变。

因此「重叫后位次必须能由过号前位次重放、不得无故沉底、墙与列表同刷原位语义」
由数据模型本身保证，而非多个写路径各自维护。

## 并发控制：重叫与占窗同成败

SQLite 写事务统一经 `db.write_tx()`：

- `isolation_level=None`（autocommit）+ 显式 `BEGIN IMMEDIATE`，
  事务一开始即取 RESERVED 锁，全局写事务串行化；配合 `busy_timeout` 排队而非立刻报锁；
- 临界区内用**条件 UPDATE 的 `rowcount` 守卫**做并发判定，任一步失败即抛错、
  整事务 ROLLBACK：
  - 号牌守卫 `WHERE id=? AND status='过号'`（重叫）/ `status='等候'`（叫号）；
  - 窗口守卫 `WHERE id=? AND current_ticket_id IS NULL`。

由此保证：

- 同号并发重叫：仅一个事务 `rowcount=1` 成功，落败方回滚，**无双占窗、无重复事件**；
- 重叫与新叫号抢同一窗：仅一个落窗，落败方号牌状态/窗口指针均无副作用；
- 重叫的号牌状态、窗口当前号指针、事件在同一事务提交，**同成败**，不存在半刷；
- 总览「办理中」桶由状态统计，与窗口指针数天然一致。

> 串行化下落败事务在胜出方提交后才进入临界区，通常先撞上前置状态校验（400）；
> 条件 UPDATE 守卫（409）作为纵深防御，防未来重构破坏不变量。两者拒因均为明确中文。

## 一次重叫必须同刷的投影

重叫事务提交后，下列读路径在同一数据状态下自洽：
重叫回执（号牌字典）、窗口当前号指针、过号回收列表（该号出队）、
等候墙（在办栏承接、种类栏不再含该号）、叫号事件（追加一条「重叫」）、
总览办理中/过号桶。前端重叫成功后重新拉取即与后端同源，无需本地拼状态。
